# Architecture

Where code lives, how a request flows, and what each layer is forbidden to do.
Read [`design.md`](design.md) first for _what_ we are building; this document is
_how_ it is put together.

The structure is inherited from
[ScottyStack](https://github.com/scottylabs-labrador/ScottyStack). The layering
contract below is not a suggestion — it is checked in review, and most of the
project's correctness properties depend on it.

---

## 1. Request path

```text
React component
  -> $api.useQuery("get", "/v1/...")                   openapi-react-query
  -> openapi-fetch, typed by apps/server/build/swagger.d.ts
  -> Express route registered from apps/server/build/routes.ts   (generated by tsoa)
  -> apps/server/src/controllers/*.ts                  tsoa decorators only
  -> apps/server/src/services/*.ts                     queries + permission checks
  -> drizzle -> PostgreSQL
```

Types flow the other way and are never hand-written:

```text
packages/db/src/schema/*.ts   drizzle table -> $inferSelect
  -> service return type (inferred, or annotated explicitly on list endpoints)
  -> tsoa reads the TypeScript type
  -> bun run build:api  =>  build/swagger.yaml  =>  build/swagger.d.ts
  -> apps/web imports `paths` and gets end-to-end typing
```

Because the web app imports from `apps/server/build/`, **`bun run build:api` must
run before any web typecheck or test.** `turbo.json` encodes the dependency as
`"build": { "dependsOn": ["^build", "@recruit/server#build:api"] }`, but the test
and typecheck tasks do not infer it, which is why it is a documented manual step.

Email and other side effects do not travel this path. A service writes a row to
`notification_outbox` inside its transaction and returns. `apps/worker` drains it
out of band. See section 6.

## 2. Layering contract

| Layer                         | Owns                                                                            | Must not                                    |
| ----------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------- |
| `packages/db`                 | tables, relations, migrations, inferred row types                               | contain business logic                      |
| `packages/access-control`     | CASL abilities, `can*` predicates, the Drizzle `WHERE` compiler                 | import the db client — types only           |
| `packages/common`             | pure domain functions: scoring, conditional-rule evaluation, status transitions | touch the db, the network, or `process.env` |
| `apps/server/src/services`    | every drizzle query, every permission check, every `HttpError`                  | know about Express                          |
| `apps/server/src/controllers` | tsoa decorators, request interfaces, delegation                                 | contain logic or touch the db               |
| `apps/web/src/routes`         | routing, loaders, page composition                                              | re-implement a permission rule              |
| `apps/worker/src`             | draining the outbox, scheduled jobs                                             | expose an HTTP surface                      |

Two of these constraints are doing specific, load-bearing work and are worth
spelling out.

**`packages/access-control` imports types only.** That is what allows the
identical predicate to run in the browser — to decide whether to render a button
— and on the server, to decide whether to permit the request. If it imported the
db client it could not be bundled into the web app, and the two would drift into
separate implementations of the same rule. That drift is how authorization bugs
are born.

**`packages/common` is pure.** No database, no network, no environment. This is
what [`product-rules.md`](product-rules.md) section 2 requires: every aggregate
has to be reproducible by hand and exhaustively testable in isolation. Services
call `common`; `common` never calls a service.

## 3. Authorization

Two tiers, applied to every resource. The full model, including the role
vocabulary and the invitation flow, is in [`authorization.md`](authorization.md).
The mechanics:

**Read visibility compiles to SQL.** `drizzleWhere("read", "Subject", user,
table)` turns CASL rules into a Drizzle `SQL` predicate that is `and()`-ed into
every query — including the pre-checks performed before an update or a delete. A
row the caller cannot see yields **404, not 403**, so the platform never leaks
that a record exists.

**Mutation authority is a predicate.** After fetching a visible row, the service
calls `canUpdateX({ user, x })` and throws 403 on failure. Creation is checked up
front, before any query runs.

Ownership is never expressed as a hand-written `eq(table.userId, user.id)`. It is
a CASL rule, so the identical predicate gates interface affordances in the
browser and enforces them on the server. Interface hiding is never the only
mechanism.

A visibility rule that is needed in more than one place is **exported and
reused**, never restated. A second copy of a visibility rule is a second place
for it to drift, and these rules decide who may read an applicant's work. The
previous version's `visibleApplicationWhere` is the pattern.

### Identity

`user.id` is the **Andrew ID**, assigned by a Better Auth
`databaseHooks.user.create.before` hook that reads the `full_email` JWT claim —
not `email`, which is the CMU alias when the person has set one. Every grant,
assignment, and review points at that id, so getting it wrong provisions somebody
under a key nothing else references.

Better Auth's `account` table already serves the purpose the proposal's
`auth_identities` table was for: `provider_id` plus `account_id` is the provider
subject, and one user may hold several. No separate table is needed.

Global roles are `admin | user | guest`, derived from the JWT `groups` claim
against `env.ADMIN_GROUP`. **Recruitment authority is layered on top and is not
the same thing** — a global admin can create a cycle and issue grants but cannot
read applicant data. `permission_grant` rows are what grant that.

## 5. The form system

The single most important subsystem, and the one with no precedent to copy.

```text
form              one logical form: a cycle's common form, or an opening's committee form
  form_version    an immutable published snapshot, or the current mutable draft
    question      belongs to exactly one version; carries a stable question_key
```

Three invariants the rest of the system depends on:

1. **A published `form_version` is immutable.** Editing creates a new draft. This
   is what stops a director changing what a question meant after it was answered.
2. **A `form_response` names the exact `form_version` it was answered against**,
   and an `answer` may only reference a question belonging to that version. The
   database enforces the second part; see [`data-model.md`](data-model.md).
3. **Conditional visibility is structured data, evaluated by one function.**
   `packages/common/src/forms/visibility.ts` is used by the browser renderer and
   by the server submission validator. There is no second evaluator, and the rule
   is never stored as executable code.

A hidden question is not required, and an answer to a question that evaluated as
hidden is excluded from the submitted response rather than quietly retained.

The common form and committee forms share all of this — same tables, same
renderer, same validator. The only difference is ownership and what the response
attaches to.

## 6. Side effects and the worker

`apps/worker` exists so that a failing email provider cannot fail a submission.

```text
service, inside one transaction:
  write domain rows
  write notification_outbox row(s)
  commit

apps/worker, separately:
  claim pending outbox rows
  send
  record attempt, retry with backoff, or mark dead
```

The worker also owns anything on a schedule. **Do not add a `setInterval` to
`apps/server`.** The previous version did, and those timers silently assume a
single replica, which is debt that document records. Scheduled work belongs to
the worker.

## 7. Files

Applicant uploads never live in answer JSON.

```text
browser -> POST /v1/files            backend authorizes, returns a presigned PUT
browser -> PUT  <presigned R2 url>   bytes go straight to R2, never through the API
browser -> POST /v1/files/:id/commit backend validates and marks the file usable
```

The `file` table holds the object key, size, MIME type, owner, and the
application it belongs to. Downloads are short-lived presigned GETs issued only
after the backend has authorized that specific caller for that specific file.

Validation at commit time is size cap, declared MIME type, and magic-byte check.
A real malware scanner is a documented follow-up, not an assumed one.

## 8. Testing

| Level      | Tooling                                                  | Location                                               |
| ---------- | -------------------------------------------------------- | ------------------------------------------------------ |
| Pure logic | Vitest                                                   | `packages/common/test`, `packages/access-control/test` |
| API        | Vitest + supertest + PGlite running real migrations      | `apps/server/test`                                     |
| Web        | Vitest + happy-dom + MSW + Testing Library, real routing | `apps/web/tests`                                       |
| End-to-end | Playwright against a booted stack                        | `e2e`                                                  |

The API suite runs real migrations against an in-process PGlite database, so
schema mistakes surface in unit-test time rather than at deploy time.

Two operational facts:

- Adding a table means adding it to the `TRUNCATE` list in **both**
  `apps/server/test/harness.ts` and `e2e/db.ts`. Forget one and tests leak state
  between cases in an order-dependent way.
- MSW runs with `onUnhandledRequest: "error"`, so an unmocked endpoint fails
  loudly instead of hanging.

An access-control rule is not finished until a test proves the **denial** path:
the reviewer without an assignment, the director of a different committee, the
revoked grant, the expired grant.

## 9. Deployment

Railway, with the infrastructure described in code in `.railway/railway.ts`.
Four resources: `web` (Caddy serving the Vite build, the only public origin),
`server` (private network), `worker`, and Postgres with a mounted volume. Plus a
private Cloudflare R2 bucket.

Migrations run from `apps/server/docker-entrypoint.sh` when the container starts,
then it execs the server. `set -e` means a failed migration kills the container
and Railway keeps the previous deployment serving, so traffic never reaches a
half-migrated database. This is deliberately _not_ Railway's `preDeployCommand`:
having both ran the same migration twice per deploy and gave it two places to
fail.

See [`deployment.md`](deployment.md) for the full operational detail, including
the cookie and origin constraints that decide the service layout.
