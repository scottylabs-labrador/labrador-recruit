# Architecture

This document records the structure inherited from ScottyStack and where recruitment
domain code lives on top of it.

## Request path

```text
React component
  -> $api.useQuery("get", "/recruitment/...")        openapi-react-query
  -> openapi-fetch, typed by apps/server/build/swagger.d.ts
  -> Express route registered from apps/server/build/routes.ts   (generated by tsoa)
  -> apps/server/src/controllers/*.ts                tsoa decorators only
  -> apps/server/src/services/*.ts                   queries + permission checks
  -> drizzle -> PostgreSQL
```

Types flow the other way and are never hand-written:

```text
packages/db/src/schema/*.ts   drizzle table -> $inferSelect
  -> service return type (inferred, or annotated explicitly on list endpoints)
  -> tsoa reads the TypeScript type
  -> bun run build:api  =>  build/swagger.yaml  =>  build/swagger.d.ts
  -> apps/web imports `paths` and gets end-to-end typing
```

Because the web app imports from `apps/server/build/`, `bun run build:api` must run before
web typecheck or test. `turbo.json` encodes this as
`"build": { "dependsOn": ["^build", "@labrador/server#build:api"] }`.

## Layering contract

| Layer                         | Owns                                                            | Must not                          |
| ----------------------------- | --------------------------------------------------------------- | --------------------------------- |
| `packages/db`                 | Tables, relations, migrations, inferred row types               | Contain business logic            |
| `packages/access-control`     | CASL abilities, `can*` predicates, the Drizzle `WHERE` compiler | Import the db client — types only |
| `apps/server/src/services`    | Every drizzle query, every permission check, `HttpError`s       | Know about Express                |
| `apps/server/src/controllers` | tsoa decorators, request interfaces, delegation                 | Contain logic or touch the db     |
| `apps/web/src/routes`         | Routing, loaders, page composition                              | Re-implement permission rules     |

## Authorization

Two tiers, applied to every resource.

**Read visibility compiles to SQL.** `drizzleWhere("read", "Subject", user, table)` turns
CASL rules into a Drizzle `SQL` predicate that is `and()`-ed into every query — including
the pre-checks performed before an update or delete. A row the caller cannot see yields
**404, not 403**, so the platform never leaks that a record exists.

**Mutation authority is a predicate.** After fetching a visible row, the service calls
`canUpdateX({ user, x })` and throws 403 on failure. Creation is checked up front before
any query runs.

Ownership is never expressed as a hand-written `eq(table.userId, user.id)`. It is a CASL
rule, so the identical predicate runs in the browser to gate interface affordances and on
the server to enforce them. Interface hiding is never the only mechanism.

### Identity

`user.id` is the Andrew ID, assigned by a Better Auth `databaseHooks.user.create.before`
hook that reads the `full_email` JWT claim. Global roles are `admin | user | guest`,
derived from JWT `groups` against `env.ADMIN_GROUP`.

Recruitment permissions are **layered on top** of that, not a replacement for it. A
`recruitment_memberships` row grants a user a `reviewer`, `committee_lead`, or
`recruitment_admin` role within a specific cycle, optionally scoped to one committee. The
global `admin` role is not the same thing as a recruitment admin.

## Where recruitment code lives

```text
packages/db/src/schema/
  recruitment.ts            cycles, committees, memberships
  applications.ts           applicants, applications, answers, preferences, candidacies
  reviews.ts                rubrics, criteria, assignments, reviews, scores
  decisions.ts              committee decisions, final placements
  imports.ts                imports, import rows
  audit.ts                  audit events

packages/access-control/src/
  types.ts                  subjects (Pick<>s of rows), RecruitmentRole
  abac.ts                   ability builder
  permissions.ts            can* helpers — the public API

packages/common/src/recruitment/
  scoring.ts                pure weighted-score and aggregate math
  disagreement.ts           pure threshold rules
  ranking.ts                pure sort and tie handling

apps/server/src/services/
  recruitmentCycleService.ts  importService.ts        applicantService.ts
  candidacyService.ts         assignmentService.ts    reviewService.ts
  aggregateService.ts         decisionService.ts

apps/server/src/controllers/
  one controller per service, named <Domain>Controller

apps/web/src/routes/recruitment/
apps/web/src/components/recruitment/
```

Scoring, aggregation, disagreement detection, and ranking live in `packages/common` as
**pure functions with no database or network access**. They are exhaustively unit tested in
isolation. Services call them; they never call services. This keeps the math auditable,
which [`product-rules.md`](product-rules.md) requires.

## Testing

| Level      | Tooling                                                  | Location                                               |
| ---------- | -------------------------------------------------------- | ------------------------------------------------------ |
| Pure logic | Vitest                                                   | `packages/common/test`, `packages/access-control/test` |
| API        | Vitest + supertest + PGlite running real migrations      | `apps/server/test`                                     |
| Web        | Vitest + happy-dom + MSW + Testing Library, real routing | `apps/web/tests`                                       |
| End-to-end | Playwright against a booted stack                        | `e2e`                                                  |

Adding a table means adding it to the `TRUNCATE` list in **both**
`apps/server/test/harness.ts` and `e2e/db.ts`.

MSW runs with `onUnhandledRequest: "error"`, so any endpoint a test forgets to mock fails
loudly rather than hanging.
